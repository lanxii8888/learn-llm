# 06 · 评估（Evaluation）

> 路线图原话：「这是区分业余和专业的分水岭。」这一篇解释为什么，以及一个最小可用的评估器长什么样。

## 没有评估会发生什么

你改了一句 system prompt，感觉变好了；又换了个更短的摘要 prompt，感觉也不错。几周后回头看：

- 早就能答对的问题，现在答错了；
- 原本会写文件的，现在只口头总结；
- 上下文一压缩就丢关键信息，但没人发现。

**「感觉」不是反馈信号。** 没有评估，每一次 prompt 改动都是盲改；有了评估，至少能回答「这次改动是变好还是变坏」。

## 评估的三要素

1. **用例集（eval set）**：一组有代表性的任务，覆盖核心能力与边界。
2. **判定（judge）**：怎么算通过。
3. **指标（metric）**：通过率、步数、耗时、成本。

### 用例怎么选

从真实使用出发，按能力分组，而不是按实现分组：

- 基础：列文档、检索、读文件；
- 组合：读多份并总结、写文件；
- 边界：超长任务（触发压缩）、空结果、不存在的文件；
- 回归：每次修 bug 都把它变成一条用例。

本项目 [eval.ts](../project/src/eval.ts) 目前有 5 条，覆盖前四类中的大部分。README 的练习会让你加第 6 条。

### 判定怎么选

| 方式 | 优点 | 缺点 |
|---|---|---|
| 确定性检查（关键词/文件/步数/是否压缩） | 快、便宜、无方差 | 脆弱，不理解同义表达 |
| LLM judge（让另一个模型打分） | 能评价语义与质量 | 有方差、要花钱、judge 自己也会错 |
| 人工 | 最准 | 最慢最贵 |

**推荐组合**：能用确定性检查的先用，语义质量再用 LLM judge 补充，人工只审高风险样本。

本项目的判定刻意简单：

```ts
containsAny('过时', '截止')         // 同义表达给多个候选
containsAll('rag.md', 'transformer.md', 'agent.md')
fileWritten('eval-rag-agent.md', 30) // 检查产物而不只是话术
compacted                            // 检查机制是否触发
```

最后一条很重要：**别只评估最终答案，也要评估过程**。答对了但用了 10 步、或者根本没压缩却硬塞，都是质量问题。

## 本项目的评估器设计

看 `runEval()`：

1. **每个用例用全新 agent**：不共享消息历史、不挂记忆，避免用例之间互相污染。评估必须可重复。
2. **清空上一轮的 `eval-*` 输出**：防止「上次写过的文件」让这次白捡分。
3. **`useMemory: false, extractMemory: false`**：评估的是 agent 能力，不是记忆抽取，也顺便省钱。
4. **预算可覆盖**：上下文保护用例用 `budgetTokens: 1200` 强制触发压缩。
5. **报告三项**：每项检查的通过情况、用例整体是否全过、总通过率。全过的用例才算「用例通过」，部分通过单独显示。

运行：

```bash
pnpm eval:stage3
# 或交互里 /eval
```

## 局限，必须说清楚

一个诚实的评估器要说明自己测不到什么：

- **关键词检查不理解语义**：模型说「知识会陈旧」而不是「过时」，就会被判错。缓解办法是多给同义词，但永远不全。
- **单次采样有方差**：`temperature` 不是 0，同一条用例跑两次结果可能不同。生产上要 `pass@k`（跑 k 次算成功率）或多次取平均。
- **没有覆盖质量**：答案正确但啰嗦、结构差，本项目判不出来。需要 LLM judge。
- **成本与延迟没纳入**：本项目只报告步数与耗时，没有设阈值。生产要设「P95 延迟」「单任务成本」预算。
- **用例太少**：5 条只能防大倒退，不能证明「好用」。

## 生产环境还要补什么

- **回归集持续增长**：每个线上 bad case 都沉淀成用例。
- **LLM judge + 人工抽检**：确定性与语义评估分层。
- **可观测性**：tracing 记录每一步的输入输出、token、耗时、工具调用（阶段 5）。
- **A/B 与灰度**：prompt/模型变更先在评估集跑，再小流量上线。
- **成本与延迟指标**：和通过率一起看，否则会优化出「又贵又慢的满分」。
- **危险用例**：提示注入、越权工具调用、超长输入，单独一组。

## 练习

1. 跑一次 `pnpm eval:stage3`，记下基线通过率。
2. 故意把 system prompt 里的「最终必须调用 write_file」删掉，再跑一次，看写文件用例是否失败——这就是评估的价值。
3. 加一条「不存在的文件」用例：要求读 `nope.md`，检查 agent 是否换用 `list_docs` 而不是死磕，答案里说明文件不存在。
4. 把某条检查从 `containsAny` 改成 LLM judge，对比两者的稳定性与成本。

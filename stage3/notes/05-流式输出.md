# 05 · 流式输出与交互体验

## 为什么值得单独讲

Agent 的最大交互问题不是「答得对不对」，而是「等得慌」。一次多步任务可能要 10–30 秒才给出最终答案：

- 非流式：转圈 → 突然出现一整段；
- 流式：第一个字几百毫秒就出来，用户知道它没死。

流式不改变 agent 的逻辑，但显著改变**感知延迟**和**可中断性**（用户能提前叫停）。

## 原理：SSE 与 delta

服务端不再等整段生成完再返回，而是通过 Server-Sent Events 持续推送增量：

```
data: {"choices":[{"delta":{"role":"assistant"}}]}
data: {"choices":[{"delta":{"content":"RAG"}}]}
data: {"choices":[{"delta":{"content":" 是"}}]}
data: {"choices":[{"delta":{"content":"……"}}]}
data: [DONE]
```

SDK 把它包装成异步迭代器，于是代码是：

```ts
const stream = await client.chat.completions.create({ ..., stream: true });
for await (const chunk of stream) {
  const delta = chunk.choices[0]?.delta;
  if (delta?.content) process.stdout.write(delta.content);
}
```

## 坑一：流式下的 tool_calls 是分片的

非流式时，`message.tool_calls` 是一个完整数组。流式时它被拆成多次 delta：

```
delta.tool_calls[0] = { index: 0, id: "call_abc", function: { name: "read_", arguments: "" } }
delta.tool_calls[0] = { index: 0,                    function: { name: "file", arguments: "{\"file" } }
delta.tool_calls[0] = { index: 0,                    function: {                  arguments: "name\":\"rag.md\"}" } }
```

注意：

- `index` 用来区分第几个调用（可能并行多个）；
- `id` 和 `name` 通常只在第一片出现；
- `arguments` 是**字符串增量**，必须按顺序拼接，拼完才是可解析的 JSON。

所以 [agent.ts](../project/src/agent.ts) 的 `callStreaming()` 用一个 `Map<number, {id,name,args}>` 累积，流结束后再按 index 排序重建完整调用。如果直接拿每一片当完整调用去执行，得到的一定是残缺参数。

```ts
const cur = calls.get(tc.index) ?? { id: '', name: '', args: '' };
if (tc.id) cur.id = tc.id;
if (tc.function?.name) cur.name += tc.function.name;
if (tc.function?.arguments) cur.args += tc.function.arguments;
```

**关键认知：流式只是「传输方式」，agent 的循环逻辑完全不变。** 拿到的还是同样的 `content` 和 `tool_calls`，后面的入历史、执行、回填都一模一样。

## 坑二：思考文本与最终答案混在一起

本项目里，模型在调用工具前可能输出一句推理（Thought）。流式时这句话会先被打印出来，然后才执行工具、再打印下一段。所以终端看起来是：

```
助手 > 我先看看有哪些文档。
  [tool] list_docs()
助手 > 找到 rag.md，读一下。
  ...
助手 > （最终总结……）
```

这其实是**好事**：用户看到了 agent 的思考过程，可解释性更强。但要做两件事：

- 工具执行的日志要和正文视觉区分（本项目用缩进和 `[tool]` 前缀）；
- 最终统计信息放在正文结束后，避免打断流。

## 坑三：计量与 `usage`

流式时 `usage` 默认不返回。需要显式开启：

```ts
stream_options: { include_usage: true }
```

开启后，**最后一个 chunk** 才带 usage（而且可能是空 choices）。但很多中转站不支持这个参数，甚至可能直接报错。所以本项目采用与阶段 2/3 一致的启发式估算（[tokens.ts](../project/src/tokens.ts)），并把真实 usage 作为「有则更好」的可选项。生产环境应优先用服务端计量。

## 与上下文工程、记忆抽取的关系

- 流式发生在「调用模型」这一层，**压缩和记忆都不受它影响**；
- 但要注意顺序：先 `fit()` 压缩、再发起流式请求；
- 记忆抽取是回答之后的**独立调用**（非流式即可），不应该阻塞用户看到最终答案——本项目先返回答案、再抽取，控制台上会看到答案之后才出现 `[记忆+]`。

## 交互体验的几条实践

1. **首字优先**：系统提示里让模型先给一句「我准备先查什么」，用户立刻有反馈。
2. **分阶段提示**：工具调用前打印一行状态，长任务不至于静默。
3. **可中断**：至少支持 Ctrl+C；进阶是检测用户输入并 abort 请求。
4. **别刷屏**：工具输出不要原样全打，只打摘要（本项目 trace 里也只保留前 300 字符）。
5. **失败也要流式友好**：流到一半报错，要明确告诉用户「已生成部分作废」，避免拼出一个半截答案。

## 练习

1. 关掉 `onDelta` 跑同一个问题，对比「等待感」。
2. 在 `callStreaming` 里打印每一个 tool_calls delta 的 index/name/args，亲眼看分片怎么拼起来的。
3. 给 `stream_options: { include_usage: true }` 加上，观察你的中转站是否支持、最后一个 chunk 长什么样。
4. 试着在流式过程中记录第一个 delta 的时间，量化「首字延迟」。

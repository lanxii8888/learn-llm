# 04 · 结构化输出（Structured Output）

## 为什么需要

当模型输出只给人看时，一段自由文本就够了。但当输出要给**程序**消费时，自由文本就是灾难：

- 想把「长期记忆」写进 JSON 文件 → 得解析自然语言；
- 想统计 agent 的检索结果 → 得写正则；
- 想在两个 agent 之间传数据 → 更不可能。

结构化输出要解决的就是：**让模型产出符合约定 schema、程序可以直接用的数据**。

## 四种手段，从弱到强

| 手段 | 原理 | 可靠性 | 兼容性 |
|---|---|---|---|
| Prompt + 要求 JSON | 在提示词里给 schema，让模型自觉 | 中 | 最好 |
| `response_format: { type: 'json_object' }` | 服务端保证是合法 JSON | 较高 | 多数支持 |
| `response_format: { type: 'json_schema', strict: true }` | 服务端按 schema 强制生成 | 最高 | 部分模型/中转站不支持 |
| Function calling | 把结果定义成工具的 `parameters` schema | 高 | 支持 tools 即可 |

一个容易忽略的点：**function calling 本身就是一种结构化输出**。模型必须按 `parameters` 的 JSON Schema 填参数，否则调用不成立。所以如果模型已经支持 tools，很多「要结构」的场景可以复用工具参数，而不是另起一套。

本项目的 `askJson()` 选的是**第一种（prompt + 校验 + 重试）**，理由很实际：中转站对 `response_format` 的支持参差不齐，prompt 方案最可移植。生产上可以「能用 json_schema 就用，不能就降级到 prompt + 校验」。

## 四层保险

看 [structured.ts](../project/src/structured.ts)：

### 1. Schema 写进提示词

```ts
输出要求：只输出一个符合下面 JSON Schema 的 JSON 对象。
不要输出任何解释，不要用 Markdown 代码块。
JSON Schema:
{ ... }
```

### 2. 从文本里抠 JSON

模型经常不听话：套 ```json 围栏、前面来一句「好的，结果如下」。`extractJson()` 先剥围栏，再取第一个 `{` 到最后一个 `}`，然后 `JSON.parse`。

### 3. Schema 校验

`validateJson()` 是手写的极简校验器：类型、必填字段、未定义字段、数组元素、枚举。别小看这一步——模型最常见的问题恰恰是：

- 少字段（`facts` 没了）；
- 多字段（自作主张加 `confidence`）；
- 类型漂移（数字写成字符串）。

### 4. 失败重试（自愈）

校验错误不是直接抛给用户，而是回填给模型：

```
user: 上次输出不合格：$.facts 应为数组，实际是 string。请只重新输出修正后的 JSON。
```

这就是「让模型自己修」。通常一次重试就能过；`attempts` 默认 2，仍失败才抛错。调用方（`extractMemories`）再兜一层 try/catch——**记忆抽取失败不能影响主回答**。

## 值得注意的工程细节

- **`temperature: 0`**：结构化任务要稳定，不需要创造力。
- **`max_tokens`**：给足但别无限，防止模型输出一大段无关内容。
- **不要在重试时丢掉错误信息**：错误喂回去，模型才知道改哪。
- **中文 JSON**：中文做 key 也能跑，但英文 key 更省 token、更稳，建议 schema 用英文键。
- **Schema 要保守**：字段越少、约束越简单，模型越不容易错。别把整个业务模型塞进去。
- **校验器与 schema 必须一致**：本项目是同一个对象驱动两者；如果分开维护，很容易漂移。

## 本项目的实际用法

在 [agent.ts](../project/src/agent.ts) 的 `extractMemories()`：

```ts
const schema: JsonSchema = {
  type: 'object',
  properties: {
    facts: { type: 'array', items: { type: 'string' } },
  },
  required: ['facts'],
};
```

模型返回 `{ "facts": ["用户在做 agent 开发学习项目……"] }`，校验通过后逐条写入长期记忆。如果返回 `{"facts": "..."}`（类型错），校验器报 `$.facts 应为数组`，模型收到错误重写一次。

## 常见错误

- 只靠 prompt，不做校验 → 模型偶尔漏字段，程序崩溃。
- 校验失败直接抛异常 → 一个格式问题毁掉整个任务。
- 用 `JSON.parse` 硬解析带围栏的文本 → 大量无谓失败。
- Schema 太复杂 → 模型在新字段上反复犯错，重试也救不回来。
- 忽略中转站差异 → `response_format` 被静默忽略，还以为生效了。

## 练习

1. 给 `facts` 的 schema 加一个 `category` 字段（`enum: ['偏好', '背景', '结论']`），观察模型是否会漏填、校验器如何报错、重试是否修好。
2. 故意把抽取 prompt 改成「随便说说」，跑一次，看 `askJson` 需要几轮才成功——体会「提示词约束」和「程序校验」缺一不可。
3. 把你自己的一个真实需求（比如「把评估结果整理成 JSON」）用 `askJson` 实现，先写 schema 再写 prompt。

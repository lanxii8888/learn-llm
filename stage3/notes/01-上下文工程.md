# 01 · 上下文工程（Context Engineering）

## 为什么这是阶段 3 的第一主题

Agent 每走一步，都会把**整段历史**重新发给模型——system、用户任务、之前所有的 tool_calls、所有的工具结果、所有的中间回答。它没有「记住」的能力，历史就是它唯一的记忆。

于是历史只会单调变长：

```
第1步：system + user                         ≈ 300 token
第2步：+ assistant(tool_calls) + tool 结果    ≈ 900 token
第3步：+ 又一次调用与结果                     ≈ 1500 token
...
```

后果是四个，按出现顺序：

1. **撞窗口**：超过模型上下文上限，API 直接报错，agent 崩。
2. **变贵**：每步都为全部历史付费，步数一多成本是平方级增长的。
3. **变慢**：输入越长，首 token 延迟越高。
4. **变笨**：真正相关的信息被埋在大量无关的工具输出里，模型注意力被稀释。

> 「上下文工程」不是「写更长的 prompt」，而是**决定每一刻到底让模型看到什么**。

## 四类基本策略

| 策略 | 做法 | 优点 | 代价 |
|---|---|---|---|
| 截断（truncate） | 超长内容只留开头/结尾 | 简单、零成本 | 直接丢信息 |
| 滑窗（sliding window） | 只保留最近 N 条 | 现状一定新鲜 | 早期的关键结论会丢 |
| 摘要（summarize） | 让模型把旧历史压成要点 | 保留语义、压缩比高 | 多一次调用，summary 本身可能失真 |
| 外部化（externalize） | 把历史写进文件/记忆库，需要时检索 | 理论上无上限 | 复杂，检索可能漏 |

生产系统通常是组合使用。本项目用的是「摘要 → 截断 → 丢旧轮」的三级降级。

## 本项目的实现：`ContextManager.fit()`

看 [context.ts](../project/src/context.ts) 的 `fit()`，每次**调用模型之前**都会走一遍：

### 第一步：找安全切点

```ts
let cut = Math.max(1, messages.length - this.keepRecent);
while (cut > 1 && messages[cut]?.role !== 'user') cut--;
```

从「保留最近 `keepRecent` 条」开始，一路往前退到最近的 **user 消息**。

**为什么必须退到 user 边界？** 因为历史里有强结构配对：一条 `assistant` 的 `tool_calls` 后面必须跟着若干条 `tool` 结果，靠 `tool_call_id` 一一对应。如果从中间切掉，模型会看到「有结果没调用」或「有调用没结果」，轻则报错，重则胡编。user 消息天然是每轮任务的起点，从那里切最安全。

这也解释了一个局限：**单轮任务内部无法做摘要压缩**（整轮都是「user → 一堆 tool 调用」），只能靠第二步的硬截断。这是设计取舍，不是 bug。

### 第二步：摘要旧历史

把要丢弃的那段交给模型，用一个专门的压缩 prompt 产出 ≤300 字的要点，然后**替换**成一个 `system` 消息：

```
[历史摘要：为控制上下文，早先的对话与工具结果已被压缩]
- 用户要求调研 RAG 并写总结……
- 已确认：RAG 解决知识过时和幻觉……
```

有两个细节值得注意：

- **摘要 prompt 自己也要控制输入长度**（`buildTranscript` 只取头尾各 6000 字符）。负责压缩的调用如果自己就超窗，那就闹笑话了。
- **摘要失败不能拖垮主流程**：`summarize()` 抛错时退化成 `fallbackSummary()`（按角色保留每轮开头），主循环照常进行。

### 第三步：硬截断

摘要完还超预算，就把最长的 `tool` 观察正文截到前 200 字符。**只动 `content`，不动 `role` / `tool_call_id`**——结构必须完整，模型才能配对。被截断的观察会带一句提示，模型知道「这里被截了，需要的话重新调工具」。

### 第四步：丢旧轮

最后的兜底：从最早的一轮开始整轮删除（保留 system、摘要和最后一轮）。这一步是**真的有损**，`RunResult.contextNotes` 里会明确写「整轮丢弃」。能不用就不用。

## 关于 token 估算

本项目用 [tokens.ts](../project/src/tokens.ts) 的启发式：中文约 1 字符 1 token，英文约 4 字符 1 token，每条消息加 4 的固定开销。它只用于**相对判断**，误差可能到 ±20%。

真实项目应该：

- 用 `tiktoken` 或厂商的计数接口精确计量；
- 把**输出预留**算进预算（模型回答也要占窗口）；
- 用 API 返回的 `usage` 校准估算系数。

## 常见错误

- 压缩时把 `assistant(tool_calls)` 和 `tool` 消息拆散 → 模型困惑。
- 只截断正文但忘了保留 `tool_call_id` → 结构损坏。
- 把摘要消息插在历史末尾而不是原位置 → 模型误以为摘要是最新指令。
- 预算只算输入不算输出 → 还是可能撞窗。
- 无脑把窗口开到最大 → 又贵又慢，且长上下文的效果并非线性。

# 02 · 工具设计（Tool Design）

## 工具描述就是写给模型看的 API 文档

人类用 API 靠文档，模型选工具靠 `description`。描述写得含糊，模型就会：

- 该调的时候不调（不知道有这个能力）；
- 不该调的时候乱调（以为能做）；
- 参数填错（不知道格式和边界）。

所以工具设计的第一原则：**描述要回答「什么时候用 / 什么时候别用」，而不只是「这个工具是什么」**。

对照 [tools.ts](../project/src/tools.ts)：

```ts
description:
  '按关键词在语料库中全文搜索，返回命中的片段、文件名和行号。' +
  '适合「定位」资料；找到文件后请用 read_file 读正文。' +
  '关键词要短而具体（如 RAG、注意力），不要整句搜索。'
```

这句里同时给了：功能、使用时机、与其他工具的分工、参数建议。这比一句「搜索文档」有用得多。

## 粒度：拆细还是合并？

阶段 2 已经有 `list_docs / search_docs / read_file / write_file` 四个工具，阶段 3 保留了这个拆分。为什么不是「一个 `research(topic)` 全搞定」？

| 粒度 | 优点 | 缺点 |
|---|---|---|
| 粗（一个全能工具） | 模型决策少 | 内部黑盒、不可观测、错误难定位、无法复用 |
| 细（原子工具） | 每一步可观察、可组合、可复用 | 模型需要更多步、描述必须更清楚 |

**判据：一个工具应该对应一个「模型需要独立决策的动作」**。先列有哪些文档、再搜、再读，这是三个不同的决策点，拆开是对的。如果两个操作永远一起出现、模型不需要关心中间结果，就该合并。

副作用工具要单独拆：`write_file` 和 `remember` 都会改变外部状态，混在只读工具里会让模型放松警惕。

## 参数设计

- **必填项越少越好**。`read_file` 只必填 `filename`，其余有默认值，降低模型犯错概率。
- **给边界**。`max_results` 限定 1–10，`max_lines` 限定 1–400：既防模型一次要 1000 条，也防它传 `0` 或负数。
- **类型要具体**。`start_line` 用 `integer` 而不是 `string`，并在描述里写「从 1 开始」。
- **不要留歧义**。`filename` 描述里写明「例如 rag.md」，模型就不会传绝对路径。

实现里还有一层**运行时校验**（`clampInt`）：模型可能无视 schema 传字符串或超大值，工具自己必须兜住。**Schema 是建议，代码才是防线。**

## 错误处理：让模型能自救

Agent 的工具错误不是给人看的，是给模型看的。所以错误信息要分两类：

- **可恢复**：参数错了、关键词没结果、文件不存在。告诉它怎么改。
  ```
  错误（可恢复）：未找到文件「xxx.md」。先用 list_docs 查看可用文件。
  ```
- **不可恢复**：未知工具、路径越权、内部异常。告诉它别再试。
  ```
  错误（不可恢复）：未知工具「xxx」。可用工具：list_docs / search_docs / ...
  ```

这套文案直接影响 agent 的鲁棒性。对比两种写法：

```
❌ Error: ENOENT: no such file or directory, open '...'
✓  未找到文件「rag.md」。可用文件见 list_docs。
```

前者模型只能瞎猜，后者能立刻纠正下一步。阶段 2 的 `search_docs` 返回「没有找到相关内容」已经是这个思路，阶段 3 把它系统化了。

另外，**工具内部异常不要直接抛**。`executeTool` 用 try/catch 把异常包装成「不可恢复错误」文本返回，保证一轮工具失败不会炸掉整个 agent 循环。

## 输出大小：工具输出就是上下文

工具返回值会原样进入上下文。返回 1MB，就等于自杀。所以：

- `search_docs` 限制片段数（默认 5）；
- `read_file` 默认最多 200 行、单次最多 6000 字符，并提示「还有 N 行，可用 start_line 继续」；
- `list_docs` 只返回文件名，不返回内容。

这和第 01 篇的上下文工程是一体两面：**要么在工具层少返回，要么在上下文层压缩**。前者更便宜、更精确，应该优先。

## 安全边界

模型（或提示注入）会尝试越权，工具实现必须自己守门：

- `path.basename()` 去掉目录部分，防止 `../../.env` 这类路径穿越；
- 只允许读 `corpus/` 和 `output/`；
- 只允许写 `.md`，限制 20000 字符；
- 写文件前检查内容长度，避免模型传空字符串覆盖已有文件。

工具权限最小化是 agent 安全的第一道防线（阶段 5 会展开到沙箱与权限控制）。

## 练习

1. 加一个 `word_count(filename)` 工具，故意把描述写成「统计文件」，看模型会不会在 `read_file` 和它之间选错；再补上「只统计行数/字数，不返回正文，适合快速判断文件规模」，对比调用行为。
2. 给 `search_docs` 加一个 `case_sensitive` 布尔参数，观察 schema 里布尔值对模型调用的影响。
3. 故意让 `write_file` 接收 `../evil.md`，确认 `basename` 把路径挡住了。

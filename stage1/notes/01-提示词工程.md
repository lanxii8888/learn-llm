# 01 · 提示词工程（Prompt Engineering）

## 核心思想

提示词是给模型的「说明书」。写得好，模型听话；写得含糊，模型自由发挥。
对 agent 来说，**system prompt 就是 agent 的「人设 + 规则 + 可用能力清单」**。

## 一个结构化 prompt 通常包含这几块

| 块 | 作用 | 示例 |
|----|------|------|
| 角色（role） | 定义模型是谁 | 「你是一个天气预报助手」 |
| 任务（task） | 要做什么 | 「根据用户问题返回天气或计算结果」 |
| 约束（constraints） | 什么能做/不能做 | 「不要编造天气，必须调用工具」 |
| 输出格式（format） | 输出长什么样 | 「用 JSON 返回，字段为…」 |
| 示例（examples） | few-shot，给几个样例 | 「问：北京几度？答：…」 |

## 三个常用技巧

### 1. 明确指令，给约束而不是给希望
- ❌ 「请尽量准确地回答」
- ✅ 「如果你不知道，就明确说『我不知道』，不要编造」

### 2. few-shot（少样本示例）
把「输入 → 期望输出」的样例直接写进 prompt，模型会照着模仿。适合格式要求高、或任务冷门的场景。

```
把下面的句子分类为「正面/负面/中性」：
示例1：这个产品很好用 → 正面
示例2：太难用了 → 负面
示例3：还行吧 → 中性

现在分类：今天天气不错 →
```

### 3. 输出格式约束
让模型输出稳定可解析的格式。最常用 JSON：

```
请用以下 JSON 格式回答，不要输出任何多余文字：
{"answer": "...", "confidence": 0.9}
```

（结构化输出到阶段 3 会深讲，这里先知道「约束格式」这个思路即可。）

## 和 agent 的关系

在 agent 里，system prompt 通常还要额外写清楚：

- **什么时候必须调用哪个工具**（而不是自己回答）
- **调用工具的纪律**：工具返回结果后如何用、不许编造工具没返回的信息
- **结束条件**：什么情况下直接给最终答案

对照本项目 [src/chat.ts](../project/src/chat.ts) 里的 `SYSTEM_PROMPT`：

```ts
const SYSTEM_PROMPT = `你是一个有帮助的助手，可以查询天气、计算数学表达式。
规则：
- 用户问天气时，必须调用 get_weather 工具，不要自己编造天气。
- 用户问数学计算时，必须调用 calculate 工具，不要心算。
- 其他问题直接回答。回答用中文。`;
```

三行规则 = 角色 + 两个约束 + 输出语言，这就是一个最小但可用的 agent 提示词。

## 本阶段的正确心态

路线图里特别提醒过：**别把大量时间花在学提示词技巧上，够用就行。**
现在行业的重点是上下文工程、评估、可靠性这些工程问题，不是背提示词模板。
你只需要掌握「结构化 prompt + few-shot + 格式约束」这三样，能写出让模型稳定调用工具的系统提示词，就够继续往下走了。

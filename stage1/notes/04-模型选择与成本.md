# 04 · 模型选择与成本

> 你用中转站，具体价格和模型名**以你的中转站页面为准**（不同中转站差异很大）。这里讲的是通用概念，学会「怎么算账」比记住具体数字重要。

## token 计费

LLM 按 **token**（词元）收费，不是按「字数」或「请求次数」。token 大致可以理解为「一个词或词的一部分」。中文里一个字 ≈ 1~2 个 token，英文一个常见词 ≈ 1 个 token。

一次请求的花费 = `输入 token 数 × 输入单价 + 输出 token 数 × 输出单价`

关键事实：

- **输入 token 和输出 token 是分开计价的**，且**输出通常比输入贵好几倍**（生成比阅读贵）。
- 所以一个「上下文很长但回答很短」的请求，贵在输入；一个「让它长篇大论」的请求，贵在输出。

### 为什么 agent 尤其烧钱

agent 是多步循环。每一次循环 = 一次完整请求，而**每次请求都会把之前所有历史重新算一遍输入 token**。10 步循环，历史会重复计费 10 次。这就是为什么上下文工程（阶段 3）是 agent 成本的核心——省输入 token 就是直接省钱。

## 长上下文 vs 短上下文

- **长上下文模型**（如 128k、200k）能装更多历史，但**更贵、更慢**。
- 不是所有任务都需要长上下文。很多场景「短上下文 + 好的摘要策略」比「无脑塞满」更划算。

判断原则：**任务到底需要模型「看到」多少信息？** 而不是「越多越好」。

## Prompt Caching（提示词缓存）

很多 API 支持缓存：如果一段输入（比如 system prompt、工具定义、前面的历史）**和上次请求一模一样**，这部分输入就不重新计费，或按极低折扣计价。

对 agent 的启示：**把稳定不变的内容（system prompt、工具定义）放在历史最前面，变动的部分放后面**。这样前缀不变，缓存命中率高，能大幅省输入 token 成本。

（本阶段先知道「有这个机制、内容稳定排序能省钱」即可，具体缓存 API 到后面真正做 agent 时再深究。）

## 模型怎么选

阶段 1 练习，选一个**便宜、够快**的模型就够了（比如 `gpt-4o-mini` 这个级别），别一上来用最贵的旗舰。练习阶段跑得多，便宜模型省下的钱和等待时间都很有价值。

真正做产品时再按「能力 / 速度 / 成本」三角权衡：

| 维度 | 关注点 |
|------|--------|
| 能力 | 工具调用稳不稳、长指令理解、指令遵循 |
| 速度 | 首 token 延迟、总吞吐（影响交互体验） |
| 成本 | 输入/输出单价、是否支持缓存 |

## 小结

- token 是计费单位，输入输出分开算，输出更贵。
- agent 多步循环会重复计费历史，所以省输入 token 是省钱关键。
- prompt caching 能打折，前提是「稳定内容排前面」。
- 练习用便宜模型，产品再权衡。

# 03 · 对话/消息结构

## 模型是「无状态」的

LLM 本身不记得上一轮说过什么。所谓「多轮对话」，其实是**每次请求都把整段历史重新发一遍**。
所以消息历史（messages）就是 agent 的「短期记忆」。搞懂消息结构，就是搞懂 agent 的记性从哪来。

## 四种角色的语义

| role | 谁在说 | 含义 |
|------|--------|------|
| `system` | 你（开发者） | 给模型定人设、规则、约束。通常放第一条。 |
| `user` | 用户 | 用户的输入。 |
| `assistant` | 模型 | 模型的回复，**包括它返回的 tool_call**。 |
| `tool` | 工具执行结果 | 工具跑完后的结果，回填给模型。 |

一次「查天气」的完整历史长这样：

```ts
[
  { role: 'system', content: '你是天气助手，必须调用工具……' },
  { role: 'user', content: '北京今天多少度？' },
  { role: 'assistant', content: null, tool_calls: [{ id: 'call_1', function: { name: 'get_weather', arguments: '{"city":"北京"}' } }] },
  { role: 'tool', tool_call_id: 'call_1', content: '北京 当前天气：晴，气温 5°C' },
  { role: 'assistant', content: '北京今天晴天，气温 5 摄氏度。' },
]
```

## 几个关键点

### 1. assistant 消息里可以同时有 content 和 tool_calls
当模型决定调用工具时，`content` 常常是 `null`，真正的信息在 `tool_calls` 里。但有些模型会先「边想边说要调工具」，所以两者可能同时存在。

### 2. tool 消息必须带 tool_call_id
模型一次可能并行调用多个工具（多个 tool_call）。`tool_call_id` 就是用来把「哪个结果」对应「哪次调用」配对的。丢了它，模型不知道结果是谁的。

### 3. 顺序不能乱
消息数组按时间顺序排列。你每追加一条，都要保证顺序正确：`system → user → assistant → tool → assistant → ...`。顺序乱，模型会读不懂上下文。

### 4. 这就是「上下文窗口」的来源
历史越攒越长，最终会撞上模型的上下文上限（context window）。撞满之后怎么处理（压缩、摘要、遗忘），就是阶段 3 的「上下文工程」。

## 对照代码

看 [src/chat.ts](../project/src/chat.ts) 里的 `Conversation` 类：

- `this.messages` 就是那份「会不断增长的短期记忆」

## 练习

跑起来后输入 `/dump`，对着你刚才的一次「查天气」交互，逐条数一下 messages 里出现了哪几种 role、顺序对不对。这是理解 agent 循环最直观的方式。

# 02 · 手写循环与步数上限

## 循环长什么样

见 [src/agent.ts](../project/src/agent.ts) 的 `run()`。骨架伪代码：

```
while 未完成 and 步数 < MAX_STEPS:
    把 消息历史 + 工具定义 发给 LLM
    if LLM 返回 tool_call:
        执行对应工具，拿到结果
        把工具结果追加进消息历史   # 关键：结果必须回填，模型才能继续
    else:
        返回最终答案，结束
```

和路线图里给的伪代码一一对应。

## 为什么要限制最大步数（MAX_STEPS）

这是阶段 2 验收的第一问。原因有三：

1. **防止死循环**：模型可能在工具调用上打转——工具报错就重试、搜索没结果就换关键词、读到的内容不满足就反复读。没有上限，它可能永远不给最终答案。
2. **成本兜底**：每一步都是一次完整的 API 请求，都要重新计费整段历史。10 步和 100 步的 token 成本差一个数量级。步数上限 = 单次任务的花费上限。
3. **可观测的失败信号**：`MAX_STEPS` 用尽还没结束，本身就是个重要信号——说明任务太大（要拆解）、工具不好用（模型用不顺手）、或 prompt 引导有误。没有上限，你就看不出 agent 其实「卡住了」。

## 上限设多少合适

本项目设 `MAX_STEPS = 12`。原则：**给足完成典型任务的步数，但足够小到能快速暴露问题**。真实项目里会结合任务复杂度、单步成本、超时预算一起调。

## 步数耗尽时怎么办

本项目的处理是返回一条明确的失败信息（而不是假装成功）。这是可靠性里很重要的一条：**失败要显式，不要静默**。生产环境（阶段 5）还会配合重试、降级、超时一起处理。

## 练习

跑起来后问一个「模糊又大」的问题（比如「把语料库所有内容都改写一遍」），观察 agent 是在第几步停下来的、`/trace` 里它卡在了哪里。这比背定义更能理解「为什么要刹车」。

# 04 · 上下文窗口管理

## 问题从哪来

agent 的每一步，都会把**整段历史**（system + user + 所有 assistant 的 tool_calls + 所有 tool 结果）重新发给模型。步数越多，历史越长。历史一旦超过模型的**上下文窗口**（context window，模型一次能处理的最大 token 数），API 就会直接报错，agent 崩溃。

所以「上下文满了怎么办」不是理论问题，是 agent 跑多步之后**必然撞上的现实问题**。

## 本项目的最小处理：预算守卫

[agent.ts](../project/src/agent.ts) 里的 `enforceContextBudget()` 做了一个最朴素的版本：

1. 设定一个**字符数预算**（`CONTEXT_BUDGET_CHARS = 60000`，真实项目应换成 token 数）。
2. 每步开始前，估算当前历史总长度。
3. 超预算时，把**最早的、最长的工具观察结果**压缩截断。

关键约束：**只压缩 `tool` 消息的 `content` 正文，不动 `role` / `tool_call_id` 这些结构**。因为模型依赖这些结构去配对调用和结果，乱动结构会让它困惑。

## 为什么说「这引出阶段 3」

本项目的预算守卫是**非常粗略**的（按字符、暴力截断），它能让你跑通多步任务，但远不是正确答案。真正的上下文工程（阶段 3 的重点）会解决：

1. **摘要（summarization）**：把旧的工具结果、旧对话总结成一小段，而不是粗暴截断。
2. **遗忘/淘汰策略**：哪些历史该丢、哪些该留（最近性 vs 重要性）。
3. **精确的 token 计量**：用 token 数而不是字符数，且要把「输出长度」也预留出来（因为输出也要占窗口）。
4. **上下文压缩**：用模型本身把冗长内容压缩成要点。

## 本阶段你只需建立这个意识

- 上下文窗口是**有限的、会满的**，这是 agent 的硬约束。
- 满之前的处理是「工程权衡」，不是「直接把窗口开大」（长上下文又贵又慢，见阶段 1 的成本笔记）。
- 阶段 3 会把这套「预算 → 压缩 → 摘要 → 记忆」完整讲透。

## 练习

故意把 `CONTEXT_BUDGET_CHARS` 调小（比如 `2000`），跑一个多步任务，`/trace` 观察历史里哪些工具结果被压缩了、模型有没有因为信息丢失而答错。这能让你直观感受到「上下文压缩是有代价的」。
